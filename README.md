# Hahaton26 — планирование выездных инженеров

MVP системы распределения заявок между бригадами (multi-crew VRPTW)
на официальных синтетических данных Beeline Business.

## Запуск

```bash
cd /c/hahaton26
venv\Scripts\activate
pytest -q
```

Текущий результат:

```text
160 passed, 0 skipped
```

(интеграционные тесты официального набора выполняются всегда —
файлы `*Синтетические данные.csv` лежат в `data/input`).

## Полный backend-сценарий через CLI

```bash
python -m src.cli plan --input-dir data/input --output data/output/plan.json
```

CLI: поиск официальных CSV → импорт → нормализация в `JobRecord` →
загрузка бригад/оборудования/локаций/матрицы → многобригадное
планирование → независимая проверка hard constraints → baseline →
сравнение → сохранение:

```text
data/output/plan.json        # основной план
data/output/baseline.json    # простой эталонный план
data/output/comparison.json  # таблица сравнения
```

Фатальная ошибка импорта (`can_skip=False`) останавливает планирование;
пустой план со статусом VALID не сохраняется.

## Streamlit-интерфейс

```bash
python -m streamlit run app.py
```

Пользовательский сценарий диспетчера:

1. **Загрузка** — демонстрационный набор или загрузка собственных CSV
   (зона выбирается для каждого файла) + готовые или собственные
   справочники JSON; дата планирования;
2. **Проверка данных** — отчёт по файлам, ошибки (файл/строка/поле),
   действия «Исправить и загрузить повторно», «Пропустить выбранные
   ошибочные записи», «Отменить загрузку»; фатальные ошибки блокируют
   расчёт;
3. **Результат** — показатели, вкладки «Назначения», «Неназначенные»,
   «Сравнение с baseline», выгрузка плана в JSON и назначений в CSV;
4. **Маршрут бригады** — стартовая точка, карта (pydeck, схематическая
   линия), таблица остановок и объяснение назначения по реальным проверкам.

Интерфейс использует тот же backend, что и CLI (`run_planning`):
импорт, ограничения, расчёт и валидация выполняются одним кодом.
Переключение вкладок/бригады не перезапускает оптимизатор.

## Входные данные (`data/input`)

```text
data/input/

    Юго-восток Синтетические данные.csv   # 83 заявки
    Югоцентр Синтетические данные.csv     # 56 заявок
    engineers.json                        # 10 синтетических бригад
    equipment.json                        # справочник оборудования
    locations.json                        # реестр локаций: location_id,
                                          #   address, latitude, longitude
    travel_matrix.json                    # направленная матрица
                                          #   (156 024 записи, geo-v1)
```

Официальные колонки CSV: `Заявка;Тип заявки BK;Тип заявки HD;Начало;Окончание;
Район;Адрес;[Подключение;]Гигабитное подключение`. Кодировка CP1251,
разделитель `;`, время Europe/Moscow. Файлы `*Контрольное распределение*.csv`
не используются. Строки «Адрес Офиса» и пустые строки не попадают в заявки.

Контрольный результат импорта: Восток 66, Юго-восток 83, Югоцентр 56,
итого 205, ошибок 0, офисов 3.

## Правила MVP (по уточнениям заказчика)

* Нормативы без заложенной дороги: CONNECTION 70, LOCAL_WORK 30,
  EMERGENCY 80, ADD_ORDER 20; занятость = фактическое время пути + норматив;
* `status = NEW`, `received_at = null`; заявки со статусами COMPLETED/
  CANCELLED исключаются из активного планирования;
* `priority` из типа работы: EMERGENCY URGENT, CONNECTION HIGH,
  LOCAL_WORK/ADD_ORDER NORMAL (бизнес-приоритет LOCAL_WORK и ADD_ORDER
  одинаковый);
* `gigabit_connection`: Да → true, Нет → false (в наборе ровно 2 гигабитные);
* `required_equipment` из конфигурации: INSTALLATION_KIT / DIAGNOSTIC_KIT /
  CUSTOMER_EQUIPMENT, + GIGABIT_TESTER при гигабите;
* бригады: `service_districts` = зона файла, `allowed_work_types` =
  квалификация, стартовая точка — офис зоны, смена 17.08.2026.

Пустые списки `qualifications`, `service_districts` и `allowed_work_types`
у бригад отклоняются при валидации — они НЕ означают «разрешено всё».

## География и матрица перемещений

`locations.json` — реестр `location_id` + адрес + координаты:

* офисы — **реальные** (приблизительные, ~1 км) координаты Москвы,
  зафиксированы в генераторе;
* адреса заявок — документированная **оценка**: базовая точка района +
  детерминированный сдвиг ±0.012°/±0.015° (~1.5 км), вычисляемый хешем
  адреса (одинаковые входы → одинаковые координаты).

`travel_matrix.json` (`matrix_version = geo-v1`) — детерминированная оценка
времени по координатам и типу транспорта (расстояние — гаверсинус):

| Транспорт         | Модель                                   |
|-------------------|------------------------------------------|
| CAR               | средняя скорость 28 км/ч                 |
| WALK              | 4.5 км/ч                                 |
| BICYCLE           | 12 км/ч                                  |
| PUBLIC_TRANSPORT  | усреднённая: детур 1.3, 20 км/ч, +10 мин |

Каждая направленная пара (origin, destination, transport_type) встречается
ровно один раз. При загрузке проверяется уникальность ключа
`matrix_version + origin + destination + transport_type`; дубликаты дают
понятную ошибку `DUPLICATE_MATRIX_KEY` ДО расчёта — молчаливая перезапись
значений запрещена (и в JSON-загрузчике, и в `TravelMatrix`, и в SQLite-слое).

## Ограничения и причины неназначения

Hard constraints: район, тип работы, требуемый тип транспорта (если задан),
оборудование, travel matrix, клиентское окно (`planned_end <= window_end`,
окончание ровно на границе допустимо), рабочая смена.

Причины неназначения:

* `NO_QUALIFIED_ENGINEER` — нет бригады по району/типу/транспорту/оборудованию;
* `NO_TRAVEL_DATA` — нет данных о времени пути;
* `NO_TIME_WINDOW` — окно не вмещает работу целиком;
* `SHIFT_CONFLICT` — подтверждённый конфликт смены (на пустом маршруте);
* `NO_FEASIBLE_INSERTION` — заявка выполнима в принципе, но жадная вставка
  не нашла позиции в текущих маршрутах (вместо прежнего SHIFT_CONFLICT).

## Baseline и сравнение

Baseline — простой эталон: заявки в зафиксированном порядке (при наличии
`received_at` — по нему, иначе — в порядке файлов и строк; допущение явно
документируется), первая подходящая бригада, добавление в конец её маршрута,
те же ограничения, что и в основном алгоритме.

Сравнение (`comparison.json`) на одинаковых заявках, бригадах и матрице:
назначения по приоритетам, неназначения по причинам, число задействованных
бригад, время и расстояние по каждой бригаде и суммарно.

Текущий прогон (набор 17.08.2026): Imported 205, Assigned **97**
(Unassigned 108, `NO_FEASIBLE_INSERTION` — ёмкость смен), Routes 10,
Used engineers 10, Validator issues 0, Plan status VALID.
Baseline: Assigned **34** (Unassigned 171). Число назначений не фиксируется
как целевое — после исправлений оно изменилось относительно прежних 73.
